## Part 1 — Daily scheduled security scan with new-finding alerts

Lovable's in-editor scanners (Wiz, agent_security, supabase_lov) can't be triggered from cron. We'll build a custom backend scan that mirrors their highest-value checks and emails `ezeoradennis20@gmail.com` only when **new** findings appear.

### What gets built

1. `**security_findings` table** — stable hash of (check_id + subject), severity, description, first/last seen, resolved_at. Service-role-only access. Used to diff "what's new" between runs.
2. **Edge function `scheduled-security-scan**` — runs the four selected check groups:
  - **RLS & policy audit**: every `public.*` table has RLS enabled; flag any policy with `qual='true'` for `anon`/`authenticated`.
  - **Grants & exposed columns**: scan `information_schema.role_table_grants` for SELECT on tables containing sensitive cols (`email`, `phone`, `*_token`, `code_hash`, `*_hash`) granted to `anon`/`authenticated`.
  - **Edge function config**: query `supabase/config.toml` mirror via a small allow-list in the function — verify `patient-actions` and `send-transactional-email` have rate-limit hits in `rate_limit_hits` within the last 24h (proxy for "rate limiter live"); flag if OTP-gated actions stop creating `booking_otps` rows.
  - **Auth settings drift**: read `auth.config`-equivalent flags via Supabase admin API (HIBP enabled, anonymous sign-ups disabled, OTP expiry ≤ 1h). Hardcoded expected baseline.
   For each detected issue: upsert into `security_findings` (update `last_seen`); collect `new` findings (no prior row or previously `resolved_at IS NOT NULL`). If any new ones, invoke `send-transactional-email` with a new `security-alert` template to `ezeoradennis20@gmail.com`. If none, send nothing.
3. **New email template** `security-alert.tsx` (React Email) listing the new findings with severity + remediation hint.
4. **pg_cron job** — daily at 03:00 UTC, invoking the function via `net.http_post` (created with `supabase--insert`, not migration, per scheduling guide). Requires `pg_cron` + `pg_net` enabled.

### Limits to call out

- This is a custom scan — Wiz / agent_security findings shown in the editor are not generated by it. The user should still occasionally open Security tab manually.
- Email goes to one address; multi-recipient can be added later.

## Part 2 — Mobile Lighthouse: LCP & TBT only (no restructuring)

Current: Performance 77, FCP 2.9s, LCP 3.6s, TBT 340ms. Per your choice, we won't defer Testimonials/BeforeAfter/SarahChat. Expected outcome: **≈ 88–92** on Slow 4G Moto G. (Hitting 100 truly requires deferring those, which you opted out of.)

### Fixes

1. **Hero image: AVIF + correct sizes**
  - Add `vite-imagetools` plugin (Vite-native, build-time).
  - Generate AVIF + WebP variants of `dental-team-{768,1280,1920}`.
  - Update `Hero.tsx` to emit a `<picture>` with `type="image/avif"` → `image/webp` → JPEG fallback. Currently 35 KB JPEG mobile drops to ~12–18 KB AVIF.
  - Fix the wrong `sizes="100vw"` (browser is downloading 1280w on a 360px screen). Use `sizes="(max-width: 768px) 100vw, (max-width: 1280px) 100vw, 1920px"` plus a `(max-width: 480px)` 480w variant so mobiles fetch a ~480px-wide image.
2. **Preload the LCP image in `index.html**`
  ```html
   <link rel="preload" as="image"
         imagesrcset="/team-480.avif 480w, /team-768.avif 768w, /team-1280.avif 1280w"
         imagesizes="100vw" fetchpriority="high" type="image/avif" />
  ```
   Generated AVIF variants get copied to `/public` (or the build emits hashed names — we'll use a small Vite plugin or copy script). Removes the ~600 ms TTFB-to-LCP gap.
3. **TBT (340 ms) — kill the biggest blockers without removing features**
  - **Drop `framer-motion`'s parallax wrapper in the Hero** (`useScroll`/`useTransform` on every scroll tick is the main mobile thread offender). Replace with plain CSS `transform` + `will-change` for the scale, and a single `IntersectionObserver` for the opacity fade. Visual identical.
  - `**fetchpriority="low"` + `loading="lazy"**` on all images below the fold (`case*-after.jpg` are 2 MB each — currently eager-decoded).
  - **Idle-load SarahChat** inside `BookingProvider`: wrap in `React.lazy` + render via `requestIdleCallback` (or 2 s timeout fallback). Chat still appears, just not in the critical path.
4. **Image hygiene (no UX change)**
  - Run the three `case*-after.jpg` (2 MB each) through `sharp` once at build to ≤ 250 KB each, JPEG q78. They are above-the-fold-adjacent in BeforeAfter; even lazy, they hurt INP when the user scrolls.

### Why not 100

Mobile 100 on a Moto G Power requires (a) eliminating framer-motion globally, (b) deferring Testimonials' continuous animation, and (c) deferring SarahChat entirely. You picked "don't restructure", so we keep all of that and target the realistic 88–92 ceiling. If after the fixes you want to push further, we can revisit then.
